# Spotify BPM/key import

Spotify downloads request scalar `audio_features` through the connected Web Player session. The existing refresh service provides caching, coalescing, timeouts and rate-limit cooldowns. Missing credentials or unavailable provider data does not fail the audio download.

Downloaded Ogg files receive `BPM` and `INITIALKEY` Vorbis tags. Automatic MP3 conversion retains them as `TBPM` and `TKEY` ID3 frames. BPM retains its fractional precision; key uses traditional notation such as `C` or `Am`. Spotify mode 1 means major, and mode 0 means minor. Unknown fields remain absent.

Completion snapshots normalized provider data into durable download evidence bound to the final file's SHA-256, size and modification time. Scanning reconciles that evidence with the canonical library song and persists effective scalar values with `spotify` provenance. Queue cleanup and reference-cache removal do not remove these downloaded facts. Imported arbitrary file tags remain excluded from effective analysis.

Analysis jobs first resolve the current source and its saved Spotify recording identity. Spotify downloads acquire that identity automatically. Unlinked tracks search Spotify by title and artist. Matching requires exact normalized title/artist and duration within 2–3 seconds; version labels are retained. Multiple qualifying releases are ranked by matching album, closest duration, then Spotify search order, so compilation album tags do not prevent a match. Missing or incompatible metadata falls back to local analysis. Automatic links retain their own provenance, never replace manual/download links, and respect explicit removals. With a connected session, analysis requests cached or fresh Spotify scalar features before decoding local audio. Complete provider BPM/key skips local decoding. Missing dimensions or lookup failures trigger the local analyzer, retaining any available Spotify dimension and filling the rest from local evidence. Cancellation releases the work claim.

Locked manual values retain precedence. Scalar Spotify features have no invented confidence, beat phase, loudness analysis or generated cues; Spotify BPM alone does not authorize deck sync. A complete Spotify result skips those local artifacts as well. Existing local artifacts are retained. To measure those artifacts independently, the combined local analyzer remains available through its local analysis entry points.

The scalar schema accepts `spotify` provenance through a transactional upgrade preserving existing results. Download-only results remain eligible for automatic analysis, so a partial download result cannot prevent local fallback. Use **Prepare library** with Spotify connected to enrich existing tracks, including those with valid local analysis. Current local audio analysis and artifacts are reused; unsuccessful lookups preserve existing results.

`scan.log` is created next to `viib.log` at application startup and appends across restarts. It includes scanner/job diagnostics, each track's filename and song ID, Spotify match/cache/failure reasons, and the resulting BPM/key values and sources. `engine="spotify+local"` indicates fallback for a missing Spotify dimension; `local_engine="reused"` means the existing audio analysis was retained instead of decoded again. These source decisions are logged even with debug logging disabled.

Spotify search diagnostics distinguish empty results, rejected recordings, timeouts, HTTP failures and rate limiting (including HTTP status and retry delay). Selection entries include eligible counts, rejection counts for title/artist/duration, the chosen Spotify ID, duration difference and selection reason.
