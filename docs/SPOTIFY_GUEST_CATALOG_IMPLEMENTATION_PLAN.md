# Spotify guest catalogue implementation plan

## Goal

Make Spotify useful in ViiB before a listener connects an account. A guest can open public Spotify links, discover music by name where a guest provider supports search, and browse the public metadata ViiB can verify. The integration runs in the existing Go backend and React/TypeScript frontend. It adds no Python runtime, helper process, or Spotify developer setup for guests.

**Compatibility requirement.** Preserve the current connected Spotify experience. A Premium listener must continue to be able to sign in through Web Player and use ViiB’s existing features without a Spotify Developer account, client ID, client secret, or redirect configuration. The optional default-browser OAuth flow keeps its existing behavior and remains a user choice. Guest availability must never determine whether connected features are usable.

## What guests should be able to do

| Priority | User action | Expected result |
| --- | --- | --- |
| First release | Paste a public track, album, artist, or playlist link or typed Spotify URI in the Spotify search field. | Show a Spotify-attributed card with title, available artwork, and **Open in Spotify**. Support `open.spotify.com` canonical links first. Qualify common short links separately using bounded redirects to approved Spotify hosts. A bare ID needs its entity type. |
| Catalogue expansion | Search by name and move through result pages. | Show tracks, albums, artists, and public playlists where anonymous support is verified for each category. Keep the search text and selected result category while navigating. |
| Catalogue expansion | Open a result or a public deep link in ViiB. | Reuse the existing artist, album, and playlist layouts where metadata is available. Show track metadata in the result view. Display album tracks, artist releases and top tracks, and public playlist items as each operation qualifies. Partial collections are visibly partial. |
| Follow-up | Inspect track credits or find a matching track already in the ViiB library. | Show verified credits on demand. Offer a local match as a suggestion after verifying the existing matching behavior against guest data. Require an explicit action before any association is saved. |
| Later candidates | Explore related artists or podcasts and audiobooks. | Consider these after the music catalogue is stable. Assess each operation’s guest coverage and value before adding it to the UI. |

Personal library, recents, account views (including the Spotify queue and Connect devices), Spotify streaming playback, downloads, and Spotify analysis refresh continue to use their existing account and plan rules. Local playback and offline imported metadata stay available independently of Spotify. Guest actions are limited to public browsing and opening the source link.

## Backend implementation

1. **Add a documented link provider in Go.** Use a dedicated read-only endpoint under `/api/spotify/guest` and Spotify’s oEmbed API. Construct upstream URLs from validated entity types and IDs. Always send a canonical `open.spotify.com` URL upstream. Spotify does not document typed `spotify:` URIs as oEmbed input, so convert them first. Return a small typed payload with entity type, ID, canonical Spotify link, title, and optional artwork. Spotify documents `thumbnail_url` and its dimensions as nullable. Keep embed markup out of the response, including the documented `html` field and the undocumented `iframe_url` field that live responses also return. Use a cookie-free HTTP client with bounded timeout and body size. Validate artwork schemes and approved hosts. Translate missing items, throttling, and upstream errors into guest-specific responses. The oEmbed reference documents tracks, albums, artists, shows, and episodes, and it accepts `open.spotify.com` and `spotify.link` URLs. Playlists are not listed, but the public playlist sample below returns valid JSON. Treat playlist oEmbed as undocumented behavior and give it its own regression check. Review the Spotify embed terms before release. Direct app-environment verification is still open. [Spotify oEmbed](https://developer.spotify.com/documentation/embeds/reference/oembed) · [Embed terms](https://developer.spotify.com/documentation/embeds/terms) · [Public playlist sample](https://open.spotify.com/oembed?url=https%3A%2F%2Fopen.spotify.com%2Fplaylist%2F37i9dQZF1DXcBWIGoYBM5M)
2. **Qualify the richer anonymous catalogue in Go.** Use SpotAPI’s documented public operations to identify candidates. Its catalogue guide lists anonymous search, track/album/artist/playlist lookup, batch lookup, playlist items, album tracks, and artist releases, top tracks, and related artists. SpotAPI is a Python library built on unofficial Web Player endpoints, and its behavior can change without notice. Check whether the existing Go Web Player contract and catalogue client can handle those operations anonymously. Keep guest authentication and token refresh isolated from the connected runtime. If the provider returns an authenticated token or unexpected identity, reject it in the guest path. Prove guest requests carry no account cookies or developer credentials. Record results for search by category, lookup by ID, collection pagination, and denied or unavailable content. Ship only operations with repeatable results. [SpotAPI catalogue](https://spotapi.readthedocs.io/en/latest/catalogue/) · [SpotAPI release verification](https://spotapi.readthedocs.io/en/latest/release-checks/)
3. **Expose qualified operations through explicit guest routes.** Use fixed resource types and bounded search text, offsets, and page sizes. Reuse the current Go query validation and public response models where compatible. Use oEmbed as a sparse link fallback when richer public metadata is unavailable. Assess the existing public playlist fallbacks independently. Apply request cancellation and concurrency limits before using a browser-backed fallback. Treat visible playlist entries as partial unless the provider confirms completeness. Preserve order, duplicates, and unavailable positions where the upstream supplies them. [SpotAPI playlist audit example](https://github.com/Aran404/SpotAPI/blob/main/examples/playlist_audit.py)
4. **Isolate failures and caching.** Use a separate guest concurrency budget, short-lived bounded in-memory cache, and cooldown with `Retry-After` handling. Key results by normalized resource or search plus locale/market when relevant. Keep guest results out of account caches, retained snapshots, download lineage, and analysis inputs. A guest failure must never mark an account disconnected, consume the connected request budget, or replay traffic through a listener’s session. Avoid logging raw links, search terms, tokens, cookies, or upstream payloads.

Implement supported behavior in native Go using repository code and independently authored adapters. SpotAPI is licensed under GPL-3.0 and ViiB is MIT-licensed. Use SpotAPI’s documentation and observed behavior only as a reference, and do not copy or translate its source into ViiB. [SpotAPI](https://github.com/Aran404/SpotAPI)

## Frontend implementation

- Render the existing Spotify search workspace for guests after session restoration. Use the same search field, familiar result cards, and detail navigation. Keep **Sign in with Spotify** visible alongside browsing. Describe the input as link lookup while that is the only qualified guest operation. Once keyword search is available, accept both forms in the same field.
- Use a guest request helper and state scoped to the guest view. Keep the connected renderer’s auth errors, cooldown, result cache, and pagination intact. On account connection, disconnection, or replacement, cancel in-flight work, reject late responses, and run the current query in the active mode where supported. Preserve input, focus, and back navigation. Clear results and controls tied to the previous mode or account.
- Render optional fields only when supplied. Provide distinct states for a missing link, an empty search, an unavailable collection, rate limiting, and retryable provider failure. Keep a sparse card useful with **Open in Spotify** even when richer fields are unavailable. Include Spotify attribution and source links in cards and detail views.
- Show only actions that apply to the current capability. Guest result cards and context menus should omit Spotify playback, queue, and download actions. Keep current connected Free, unknown-plan, Premium, and OAuth affordances and their existing server enforcement.

## Verification and release gates

| Gate | Evidence required |
| --- | --- |
| Zero-setup guest | From a fresh ViiB profile with Spotify cookies, account sessions, and developer settings absent, open one link of each supported type. Verify link validation, missing artwork, denied/private links, and recovery from upstream failure. Run the flow in browser/server and packaged desktop builds. |
| Rich public operations | Use a clean guest session for each enabled operation. Verify pagination, stable IDs, duplicate and unavailable playlist positions, partial collection handling, and `429` behavior. Compare browser-backed fallbacks with the native catalogue on completeness, latency, and resource cost. Record operation, date, region, request mode, and outcome without retaining credentials. |
| Premium regression | With no Spotify developer settings configured, verify Web Player sign-in, session restore and refresh, search and pagination, track/album/artist/playlist browsing, supported saved library and Recents, playback, queue, and a user-authorized download test. Exercise existing analysis and waveform paths through fixture tests and authorized live testing where available. Verify connected operation while guest services are unavailable or disabled. |
| Other connected modes | Verify Free and unknown-plan metadata and media controls, the optional OAuth sign-in and account views, and the existing auth-required and reconnect states. Cover session replacement, logout, and startup restoration. |
| Isolation | Exercise guest requests during sign-in, disconnect and reconnect during response reads, account replacement, malformed responses, cancellation, and guest throttling. Confirm no account state or persistence changes from guest requests and no guest access to private or write routes. |
| UI | Exercise the Spotify page and direct detail links in both modes. Cover keyboard-only input and retry, focus during sign-in transitions, responsive layouts, navigation back to results, explicit partial-data messages, and absent guest media controls. |

Run `go test ./internal/spotify/... ./internal/api` from `backend` and `npm run check` from the repo root. Add focused regression coverage for guest input and response contracts, account/guest isolation, and the signed-out UI flow. Run targeted race tests on guest client and cache state where supported. Fixtures verify request and parsing behavior. Live checks qualify provider access separately and use an authorized test account for any playback or download action.

## Delivery sequence

1. Capture the connected baseline and add guest link lookup plus the signed-out Spotify workspace. This slice ships independently after zero-setup and connected regression checks.
2. Qualify native Go anonymous search and entity reads, then enable categories and detail operations individually as evidence supports them. Keep a guest-only control for disabling the unofficial provider while link lookup and connected access continue to operate.
3. Extend catalogue depth with verified playlist and album pagination, artist releases, and credits. Evaluate local matching independently before making it an action in the guest interface.
4. Update [Spotify user documentation](spotify.md) with behavior actually shipped, and record verified guest coverage and known limits alongside existing Spotify validation docs. If a guest provider breaks after release, disable the affected guest operations and keep the documented link experience available.

The first release is complete when a fresh ViiB user can open a public Spotify link without any Spotify setup and a Premium Web Player user can still complete the connected flows with no developer credentials. Each richer guest operation has its own live and regression acceptance criteria above.
